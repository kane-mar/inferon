# 401 or 403: the key is not accepted

You sent a request and got `401`. Or you are signed in and the dashboard refuses an
action with `403`. The two are different problems. Where the key comes from is in
[Your first request](../using/first-request.md).

## Symptom

```
$ curl -s -w ' [%{http_code}]\n' https://inferon.agilefederation.com/v1/chat/completions \
    -H 'Content-Type: application/json' \
    -d '{"model":"deepseek-flash","messages":[{"role":"user","content":"hi"}]}'
{"error":{"message":"missing or invalid Authorization header","type":"invalid_api_key"}} [401]
```

In the dashboard, an owner-only action returns:

```json
{"error":{"message":"this action requires a tenant owner","type":"insufficient_role"}}
```

## What it means

A `401` with `invalid_api_key` means the gateway did not recognise the credential. The
header is missing, malformed, carries a key that was revoked, or carries a key that
belongs to a different installation. A key from the hosted service is unknown to a
self-hosted install, and the reverse is true too.

A `403` with `insufficient_role` means the gateway knows exactly who you are, and your
role is **member**. Providers, routing, budgets, payload settings and key limits are
**owner**-only. Members can read every report and create their own keys.

## Fix

1. **Check the header shape.** It is `Authorization: Bearer sk-inferon-…`. A provider
   key (`sk-…` from DeepSeek or OpenAI) belongs in **Providers**, never in your client.
2. **Check the key's status** on **Settings → API keys**: the **Status** column says
   Active or Revoked, and **Last used** tells you whether the request reached us.
3. **If it is revoked, make a new one**: **Create my key** in the Connect card, or
   **Create key** on **Settings → API keys**. The new key is shown once; update the
   client and the environment variable it reads.
4. **If this is a self-hosted install**, confirm the key was minted by *this* install.
   Copying a key from the hosted service does not work, and the reverse does not either.
5. **For a `403`**, ask an owner to make the change. A member can still create a key
   and read the reports.

## How to confirm it worked

```bash
curl -s -w ' [%{http_code}]\n' https://inferon.agilefederation.com/v1/models \
  -H "Authorization: Bearer $INFERON_API_KEY"
```

A key the gateway accepts returns `200` and a JSON list. Then the same call to
`/v1/chat/completions` returns `200` with a `x-inferon-trace-id` header, and
**Settings → API keys** shows **Last used** within a minute.

For a `403`, the same action succeeds once an owner performs it, and
**Routing → Recent changes** names the owner who did.

## When to stop and ask

- `/v1/models` returns `200` but `/v1/chat/completions` returns `401` with the same key.
- The key says Active, **Last used** is seconds ago, and the answer is still `401`.
- A `403` arrives for an action the page presents as available to you.
- You rotated `SESSION_SECRET` and now every dashboard page bounces you to sign-in:
  that is a session problem, not a key problem, and every user is affected.
